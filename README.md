# fsx-ontap-eks-lab

A hands-on lab for **Amazon FSx for NetApp ONTAP**, and for running it underneath **Amazon EKS with NetApp Trident**, built with Terraform.

It exists to answer the questions a cloud team actually asks before putting ONTAP in the cloud: what the landing zone around the file system looks like, how the tiering policies move data and what that does to cost, and how Kubernetes workloads consume ONTAP storage with snapshots and shared volumes. NetApp owns the storage expertise. This lab is about the cloud, network, security, and platform work around it.

Maintained by [NubisCore](https://nubiscore.ca).

## What it builds

| Piece | Details | Default |
| --- | --- | --- |
| Network | VPC across two AZs, private subnets, one NAT gateway | on |
| FSx for ONTAP | `SINGLE_AZ_1`, 1024 GiB SSD, 128 MBps, encrypted with a customer-managed KMS key, no automatic backups | on |
| Storage VM | `svm1`, UNIX security style | on |
| Tiering volumes | Four 10 GiB volumes, one per tiering policy: `NONE`, `SNAPSHOT_ONLY`, `AUTO`, `ALL` | on |
| Credentials | `fsxadmin` and `vsadmin` passwords generated by Terraform and stored in Secrets Manager (encrypted with the same key) | on |
| Client | `t3.micro` on Amazon Linux 2023, IMDSv2 only, no SSH key and no public IP: you reach it with SSM Session Manager | on |
| EKS | Managed node group on AL2023, pod identity agent, CSI snapshot controller, API restricted to your IP | off |
| Trident identity | IAM role (NetApp's documented FSx permissions) bound to `trident/trident-controller` through EKS Pod Identity | with EKS |
| Budget | Monthly AWS budget with alerts at 50%, 80% and 100% forecast | when an email is set |

The file system only accepts traffic from inside the VPC. Trident gets the SVM-scoped `vsadmin` account, never `fsxadmin`, and reads it from Secrets Manager rather than from a Kubernetes secret.

## Cost

FSx for ONTAP bills for provisioned SSD capacity and throughput whether or not you use them. That is the largest cost here, followed by the NAT gateway and, when enabled, the EKS control plane and nodes. Price your region in the [AWS Pricing Calculator](https://calculator.aws/) before you start, set `budget_alert_email`, and run `make down` when you stop for the day.

The one exception: the `AUTO` volume needs data to stay cold for at least two days before it tiers. If you want to see that, leave the file system up across two days; the `ALL` and `SNAPSHOT_ONLY` volumes show tiering the same day.

## Quick start

Requires Terraform 1.9+, the AWS CLI with the Session Manager plugin, and, for the Kubernetes part, `kubectl` and Helm.

```bash
cp terraform/terraform.tfvars.example terraform/terraform.tfvars   # set region and budget email
make init
make up          # FSx for ONTAP, SVM, tiering volumes, client (about 20-30 minutes)
make client      # shell on the client; see docs/lab-plan.md for the tiering exercise
make footprint   # SSD vs capacity-pool footprint per volume, from your machine
make down
```

One thing the tiering policy tables do not say: `AUTO` and `SNAPSHOT_ONLY` never tier while the SSD tier is at or below 50% utilization. The lab's four small volumes leave it near 1%, so to watch those policies actually move, set `tiering_filler_gib = 480` in `terraform.tfvars` and follow step 4 in [docs/lab-plan.md](docs/lab-plan.md). Measured results are in [docs/results](docs/results/2026-09-tiering.md).

Kubernetes, once week 1 is done:

```bash
# in terraform.tfvars: enable_eks = true, eks_public_access_cidrs = ["<your IP>/32"]
make up
make trident     # Trident operator via Helm
make backend     # TridentBackendConfig for the FSx SVM, StorageClass, VolumeSnapshotClass
make demo        # two pods writing to one ReadWriteMany volume
make snapshot    # ONTAP snapshot via the Kubernetes API, restored into a new claim
make down        # removes Trident-created volumes first, then everything else
```

`make check` runs `terraform fmt`, `validate`, and plan tests against a mocked AWS provider. It needs no AWS credentials and is what CI runs.

## Why Trident is installed with Helm

NetApp also publishes Trident as an EKS add-on (`netapp_trident-operator`), but its documented prerequisites list Amazon Linux 2 nodes, and current EKS versions no longer ship AL2 node images. The Helm chart supports AL2023, so the lab uses it. The chart version is pinned in the `Makefile` (`TRIDENT_CHART`).

## Layout

```
terraform/
  main.tf                  VPC, FSx module, client, EKS, Trident identity, budget
  modules/fsx-ontap/       file system, SVM, tiering volumes, KMS, secrets, security group
  tests/plan.tftest.hcl    offline plan tests (mocked provider)
k8s/
  backend-ontap-nas.yaml.tpl   rendered from Terraform outputs by `make backend`
  storageclass-ontap-nas.yaml  StorageClass and VolumeSnapshotClass
  demo/                        shared-volume app, snapshot and restore
docs/
  lab-plan.md              the two-week plan, step by step
  naming.md                current NetApp and AWS product names, with sources
  results/                 measured results from lab runs
```

## Not in this repo yet

- **SnapMirror replication.** Week 2 in `docs/lab-plan.md` describes it; the Terraform for a second, source file system comes next.
- **Multi-AZ, SMB with Active Directory, and iSCSI.** The security group already allows iSCSI; everything else here is single-AZ NFS.
- **Remote Terraform state.** State is local and contains the generated passwords. Use an encrypted S3 backend before sharing this with a team.
